# ReminderFoxAgain 0.9.2 — Developer's Guide

Oct 18, 2026 · David

This guide is the reference for working on the ReminderFoxAgain 0.9.2 code. It covers the Store's data API, the main process, every `window.rf` call, the renderer components and the test tools. The Technical System Design document explains why things are built this way; this guide says how to change them.

## 1. Setup and layout

You need Node.js 22. The runtime dependency is `ical.js` 2.2.1; the dev dependencies are Electron 44.7.0 and `@electron/packager` 20.3.0. The UI checks need Xvfb, and the Windows build needs makensis (apt install nsis) and its test Wine with 64-bit support (`wine`).

```
npm ci
npm test                       # unit tests (node:test)
RF_DATA_DIR=/tmp/rf npm start  # run with a throw-away data folder
node tools/sample-data.js /tmp/rf basic   # or: bills
./build.sh                     # Windows installer in dist/release/ (needs makensis)
```

### macOS and Linux builds (0.9.0)

Both build on Linux and give the same SHA-256 hashes on every run.

```sh
./build-linux.sh   # dist/release-linux/: .tar.gz and .deb for x64 and arm64 (ARCHS=x64 for one)
./build-macos.sh   # dist/release-macos/: one universal .zip (Apple silicon + Intel)
tools/test-linux-install.sh dist/release-linux/ReminderFoxAgain-0.9.2-linux-x64.tar.gz
python3 tools/check-macos-app.py dist/macos/universal/ReminderFoxAgain.app 0.9.2
```

- **Linux:** `build/linux/` holds `install.sh`, `uninstall.sh`, the menu entry, the icons and the .deb's `postinst`, `postrm` and AppArmor profile. The .deb installs to `/opt/ReminderFoxAgain`, links `/usr/bin/reminderfoxagain` and makes `chrome-sandbox` setuid root. The tarball installs per user under `~/.local`, and its launcher adds `--no-sandbox` only where unprivileged user namespaces are off.
- **macOS:** the packager builds arm64 and x64 apps. `build/macos/universal.mjs` joins them with `@electron/universal`, using `build/macos/lipo`, a small Python stand-in for Apple's `lipo`. `rcodesign` then signs the app ad hoc with `build/macos/entitlements.plist`. It isn't notarized, so users open it once with Open Anyway. `tools/check-macos-app.py` checks the result without a Mac: every Mach-O file is universal, every slice's page hashes match, the CodeResources seal holds, and the Info.plist keys are right.
- **Platform code:** `src/main.js` picks the tray icon (`trayTemplate.png` on macOS), the application menu (macOS only), start at login (Run key, Login Items or `~/.config/autostart`), the badge and alarm attention per system. `src/ui/i18n-dom.js` adapts the Windows wording and turns Ctrl+ into ⌘ on macOS before translating. `RF_FAKE_PLATFORM=darwin|linux|win32`, `RF_PRINT_MENU`, `RF_FAKE_TRAYLESS` and `RF_TEST_AUTOSTART` let `tools/e2e.sh` check all three on Linux.

## 2. The Store (`src/core/store.js`)

`new Store(text)` parses an iCalendar string (empty text makes an empty calendar) and indexes items by UID as `{master, exceptions[]}`. It exports `{ Store, DEFAULT_LIST, describeRecur, dayKey, timeKey, parseCalendars, expandAges }`.

The rule that matters most: **edit components, never rebuild them.** `upsert()` changes only the properties the editor owns and leaves the rest of the component alone, so imported and add-on properties survive. All times in and out are epoch ms or local `YYYY-MM-DD` / `HH:MM` keys. For tests, set `store.clock = () => <ms or Date>`; every “now” inside the store (LAST-MODIFIED, completion, archive stamps, remind-until-completed) goes through `_now()`.

### The item DTO (`get(uid)`, `list()`, `upsert(dto)`)

| Field | Type | Notes |
| --- | --- | --- |
| `uid` | string | Omit in `upsert` to create; new UIDs are `<uuid>@reminderfoxagain` |
| `kind` | `'event'` \| `'todo'` | VEVENT / VTODO; changing it converts the component |
| `summary`, `notes`, `location`, `url` | string | `display` = summary with `<1960>` ages expanded for the current year (read-only) |
| `categories` | string\[\] |  |
| `important` | boolean | PRIORITY 1 |
| `allDay`, `date`, `time` | bool, `YYYY-MM-DD` \| null, `HH:MM` \| null | `date: null` = undated to-do |
| `endDate`, `endTime` | key \| null | Events only; all-day ends are inclusive in the DTO, exclusive in the file |
| remind | object \| null | To-dos (0.4.0): {start: 'before'\|'date', days, date, at: 'HH:MM', every: 'once'\|'day'\|'2days'\|'week'\|'2weeks'\|'month', afterDue}. When set, alarm is null; stored as X-REMINDERFOXAGAIN-REMIND plus a standard VALARM for other apps. date on a to-do is its due-by date. |
| `repeat` | object \| null | `{freq: 'DAILY'\|'WEEKLY'\|'MONTHLY'\|'YEARLY', interval, byday[], mode: 'date'\|'weekday', nth, wd, end: 'never'\|'until'\|'count', until, count}`, or `{custom: true}` for rules the editor can't show (kept as is) |
| `repeatText` | string | Read-only, e.g. “Every 2 weeks on Thu” |
| `alarm` | object \| null | `{minutes}`: minutes before the start (negative = after; all-day −540 = 9:00 on the day, 900 = 9:00 the day before), or `{keep: true}` to leave an alarm the editor can't show |
| `completed`, `completedDate`, `doneLog` | bool, key, `{date: ms}` | Events: per-occurrence log; to-dos: STATUS:COMPLETED |
| `list` | string \| null | To-dos; `"To-Do's"` = main list |
| `untilDone`, `showInTooltip` | boolean | Add-on flags |
| `order` | number \| null | X-APPLE-SORT-ORDER |
| `archivedAt`, `archiveReason` | ms \| null, string | Set only in the archive store |
| `timezone` | string \| null | TZID of an imported start (read-only) |

**To-do reminder plans (0.4.0).** The helpers are `normRemind(r)` (validate), `readRemind(c)` / `writeRemind(c, r)`, `remindFirst(r, dueKey)` and `remindAt(first, k, step)` (the k-th fire on the local clock), and `writeRemindAlarm(c, r, dueKey, summary)` (the interoperable VALARM). `Store._remindFires(it, r, from, to)` returns the latest fire in a window, and `alarms()` emits it with key `uid|dueMs|fireAt` and `remind: true`. Converting a to-do to a reminder is `upsert({...dto, kind: 'event', date, time, allDay, alarm, remind: null, list: null})`.

In the renderer, the editor's `#edRemindBox` replaces `#edAlarmRow` for to-dos. The functions are `legacyRemind()` (an old single alarm → “once, N days before”), `renderRemind()`, `readRemindUI()`, `remindSummary()` and `showRemindParts()`. `buildEditorDto()` is shared by Save and **Schedule as a reminder…** (`__rfx.askSchedule(dto)`, which resolves to true when converted). The list shows the plan with `remindShort()` and `remindTitle()`.

### Occurrence rows

`occurrences()`, `nextOccurrences()` and `completedHistory()` return **rows**, one per occurrence:

`{uid, kind, summary (ages expanded for that year), start, end, date, time, allDay, repeating, repeatText, important, categories, hasAlarm, completed, completedAt, notes, location, list, untilDone, showInTooltip}`

They may also carry `past`, `history`, `carried`, `overdueSince` and `occStart`. A carried row (remind until completed) is drawn on today, but `occStart` is the occurrence it acts on.

### Methods

| Method | Returns | Purpose |
| --- | --- | --- |
| `get(uid)` / `list()` / `count()` | DTO / DTO\[\] / n | Read |
| `upsert(dto)` | uid | Create or update; sets LAST-MODIFIED and DTSTAMP |

| `alarms(from, to, {now})` | alarm rows | `{key: 'uid\|start\|at', uid, start, at, summary, …}` for alarms firing in \[from, to) |

| `duplicate(uid, {list, suffix}) / removeListItems(name)` | new uid / n | An exact copy (master + exceptions) under a new UID, not completed; on another list with list, right after the original in My order without it. removeListItems deletes a list's to-dos |

*Example — a repeating reminder in a test:*

```
const { Store } = require('../src/core/store');
const s = new Store('');
s.clock = () => new Date(2026, 9, 1, 8, 0);
const uid = s.upsert({ kind: 'event', summary: 'Team stand-up', date: '2026-10-05', time: '09:30', allDay: false,
  repeat: { freq: 'WEEKLY', byday: ['MO', 'WE', 'FR'], end: 'never' }, alarm: { minutes: 5 }, categories: ['Work'] });
const week = s.occurrences(new Date(2026, 9, 5), new Date(2026, 9, 12));
// week.length === 3, week[0].time === '09:30', s.get(uid).repeatText === 'Weekly on Mon, Wed, Fri'
```

## 3. The main process (`src/main.js`)

The main process owns two Store instances, `store` (lists) and `archive` (only what earlier versions left; archiveToList() empties it on start), plus the `state` object saved as `state.json`. Every handler that changes data ends in `changed()`, which saves, broadcasts `data:changed`, refreshes the tray and runs `checkAlarms()`.

### Start-up order

`loadState()` → `loadData()` → `loadArchive()` → archiveToList() → `applyNativeTheme()` → `setupIpc()` → `applyLoginItem()` → `createTray()` → `createMain(!--hidden)` → `checkAlarms()` (then every 15 s) → `armSlider()`, with the pop-up 8 s later. Then `powerMonitor` resume and unlock hooks. `RF_SCREENSHOT` switches to `screenshotMode()`.

### Settings (`state.settings`)

Defaults live in `DEFAULT_SETTINGS`. `loadState()` merges saved values over them and upgrades old shapes. `settings:set` merges a patch, saves, applies side effects, and broadcasts `settings:changed` to every window.

### Alarm keys and state

- Calendar alarm key: `uid|occurrenceStartMs|fireAtMs`. Quick alarm key: `quick|<id>|<atMs>`.
- `state.dismissed[key] = ms`, pruned after 7 days.
- `state.snoozed[key] = {until, alarm}`. The copy of the alarm row lets a snoozed alarm come back even if the item's alarm changed.
- `shownKeys` (memory only) stops the same alarm re-opening the window on every 15-second check.

## 4. The IPC interface (`window.rf`)

Every method returns a Promise. The preload calls `ipcRenderer.invoke(channel, …args)`, and each main-side handler is wrapped by `handle()` so that it returns `{ok: true, value}` or `{ok: false, error}`. The preload unwraps that: you get the value, or an `Error` with a readable message. In the renderer, wrap calls in `guard(p)` to show errors in a dialog.

| Method | Channel | Arguments → returns |
| --- | --- | --- |
| `range(from, to, opts)` | `data:range` | ms, ms, `{includeTodos}` → rows |
| `next(from, opts)` | `data:next` | ms, `{count`, until} → rows; app.js passes repeatOpts() from settings.repeatAhead |
| `history(before)` | `data:history` | ms, `{tickedOnly}` → past rows of repeating reminders; main applies `settings.pastRepeatDays` unless `tickedOnly` |
| `all()` / `get(uid)` | `data:all` / `data:get` | → DTO\[\] / DTO \| null |
| `save(dto)` | `data:save` | DTO → uid |
| `remove(uid, occ?)` | `data:delete` | → boolean |

### Events (main → windows)

`window.rf.on(channel, fn)` returns an unsubscribe function. Only these channels are allowed:

| Channel | Payload | Sent when |
| --- | --- | --- |
| `data:changed` | — | Any data change |
| `settings:changed` | settings | Settings, suspend or sound changed |
| `alarms:update` | `{alarms, settings}` | Every alarm check (alarm window) |
| `alarms:ring` | — | A new alarm joins an open alarm window |
| `ui:new` | `{kind}` | Tray → Add reminder or to-do |
| `ui:edit` | `{uid, start}` | Alarm Open, or a pop-up item clicked |
| `ui:quick` / `ui:suspend` | — | Tray menu items, or Open on a quick alarm |
| `slider:update` | `{today, upcoming, settings}` | The pop-up is shown again |

### Adding a call

1. Add `handle('area:verb', (e, …args) => …)` inside `setupIpc()` in `main.js`. Validate the arguments there, and call `changed()` if data changed.
2. Add `verb: (…args) => call('area:verb', …args)` to the object in `preload.js`. For a new event, add its name to `CHANNELS`.
3. Call it from the page as `await guard(window.rf.verb(…))`.

## 5. Renderer components

The pages are plain HTML, CSS and JavaScript, with no framework or bundler. Each script is an IIFE in strict mode, loaded in order by the page: `common.js`, then `app.js`, then `features.js`. Markup lives in `index.html`; dialogs that are built on demand (in `features.js`) create their own `<dialog>` elements.

### Translations (0.7.0)

The UI speaks the original add-on's 34 languages. English text is the key everywhere, so you write English and the translator finds it.

**Writing UI text.**

- Plain text in the markup, and text a script sets with `textContent` or `innerHTML`, is translated as it appears by `i18n-dom.js`. Nothing to do, as long as the exact text is in the catalog.
- Text put together from parts goes through `RF.T()` with placeholders, never string concatenation: `T('{n} reminders', {n})`, `T('Due by {date}', {date: fmt.date(d)})`. Names starting with `n` (`{n}`, `{n2}`) match numbers; others match any text, which is translated in turn.
- Plurals: one key per form you'd write in English (`'{n} reminder'` / `'{n} reminders'`); the values carry each language's forms, `one=… | few=… | other=…`.
- User text must not be translated: give its element `translate="no"` or one of the skipped classes (`.t`, `.chip`, `.notes`, `span.sub`).
- Main-process text (tray, tooltip, dialog titles, file filters) goes through `tr()`; the Store's repeat descriptions through `setPhrases()`.

**Adding or changing a string.**

1. Add the English line at the end of `tools/i18n/catalog.txt`; its position among the keys is its number (adding at the end keeps every other number). Aliases with the same translation share a line, joined with `||`.
2. Add the same numbered line to every `tools/i18n/<code>.txt` (`-` keeps English, for example for a product name).
3. `node tools/i18n/build.js` checks each file (missing or unknown placeholders, stray braces, line numbers) and writes `src/ui/locales/<code>.json`.
4. Find what is still English: `node tools/i18n/build.js --pseudo de` writes a pseudo-translation (⟦…⟧) as de.json; run `RF_LANG=de RF_I18N_COLLECT=/tmp/missing.txt tools/e2e.sh` (or `tools/shots.sh`) and every text that came out untranslated is listed. Put the real file back with `node tools/i18n/build.js` afterwards.
5. `npm test` (test 2 fails if a locale misses a key or a placeholder) and the language runs in `tools/e2e.sh`.

**Example — a new toast “{n} items moved”.** Write `A.toast(RF.T('{n} items moved', {n}))`, add `{n} items moved` to the catalog, add the German line `Nr| {n} Einträge verschoben` (with the catalog's number) and the other 32, build, and check it with `RF_LANG=de`.

**Right to left.** Arabic and Hebrew set `dir="rtl"` on `<html>`. Prefer logical CSS (`margin-inline-start`, `inset-inline-end`) for new rules; the RTL overrides at the end of `styles.css` cover the older ones.

**Adding a language.** Add it to `LANGUAGES` in `i18n.js` (code and native name; to `RTL` if needed), add its Chromium locale to `CHROMIUM_LOCALES` in `main.js`, write `tools/i18n/<code>.txt`, and build.

### Columns, Order and sounds (0.8.0)

**A new column.** Give its cells a `c-<id>` class in `HEAD_REM` / `HEAD_TODO` and `rowHtml()`, add the id to `COLUMNS` in `app.js` and to `COL_SETS` / `COL_NAMES` in `features.js`, and add `.listwrap.hide-<id> .c-<id>` to the hiding rule in `themes.css`. Then add it to `SORTS` (and the `#todoSort` options) if the lists should order by it.

**A new built-in sound.** Add an entry to `TONES` in `common.js`: `{ id, label, dur, draw(c, out, t0) }`, where `draw` schedules oscillators on `out` from `t0` with the `note()` helper and `dur` is its length in seconds (the continuous loop and the UI check rely on it). Add the label to the i18n catalog and every language file, run `node tools/sounds.js <dir>` to write its .wav for the mobile builds, and update the check in `view-options.js`, which lists the ids.

*Example — a soft “ping”:* `{ id: 'ping', label: 'Ping', dur: 1.2, draw(c, out, t0) { note(c, out, t0, 1568, { peak: 0.3, decay: 1.1 }); } }`.

### Keeping your place and themes (0.8.1)

**Re-rendering without losing the place.** Pass the reason `'anchor'` to `renderReminders` / `renderTodos` when rows appear or disappear above what the person is looking at: `anchorOf()` runs before the new HTML goes in and `restoreAnchor()` after. `scrollToDay(k)` scrolls the Reminders list to the first row on or after a day. Both work on `tr[data-key]` and `data-sort` (the start in ms), so new row types need those attributes.

**Themes.** A built-in theme is CSS under `:root[data-theme="…"]` in `themes.css`; your own are five colours run through `RF.themeVars()`. A new CSS token must be added to `themeVars()` too (derived from the five), or custom themes fall back to the stylesheet's value. `RF.applyTheme(id, customThemes, preview)` is the only way pages apply a theme; `RF.THEME_COLORS` gives the editor a built-in theme's five colours.

*Example — a new token `--warn` (amber notes):* add it to the `:root` blocks of each built-in theme, and in `themeVars()` return `'--warn': dark ? '#ffb74d' : '#b26a00'`.

## 7. Build, release, conventions and troubleshooting

### Release checklist

1. Bump `version` in `package.json` and `package-lock.json` (two places). The app reads its version from `package.json`.
2. Update `README.md`: a “New in x.y.z” section and the release file names. After any change to UI text, run node tools/i18n/build.js and a collect run (see Translations in section 5).
3. Run every suite: unit tests in 7 zones, `tools/e2e.sh`, `tools/test-installer.sh` and `tools/shots.sh`.
4. Run `./build.sh` twice and compare `dist/SHA256SUMS.txt`; every hash must match.
5. Ship `dist/release/*` together with a source zip (without `node_modules` and `dist`) and the screenshots.

A change to the Electron version is a full release: the installer reuses an installed runtime only when its version matches, so users then need the runtime parts.

### Conventions

- **Data compatibility first.** Never drop or rewrite properties you don't own. App-only data goes in `state.json`, or in `X-REMINDERFOXAGAIN-*` properties (such as the to-do reminder plan).
- **Time.** Store code takes “now” from `_now()`. Main-process alarm code passes `now` down. Use local `dayKey` / `timeKey` strings for dates, never `toISOString()` (it's UTC).
- **Safety.** Write files with `writeAtomic`. Write the receiving file first when moving items. Every IPC handler validates its input.
- **UI.** Escape user text with `esc()`. Call IPC through `guard()`. Use theme tokens instead of fixed colours. Make every control keyboard-reachable, with a `title` or `aria-label`. Keep messages short and in plain words.
- **Style.** `'use strict'`, IIFEs, 2-space indent, single quotes, no build step. Comments explain why, not what.
- **Tests.** Every behaviour change gets a unit test or an E2E line. Expected values are written out, never computed the same way as the code under test.

### Troubleshooting development

| Symptom | Cause and fix |
| --- | --- |
| `E2E ERROR no output from <name>` | The page threw before the first check. Run the script through the console wrapper and look for `RF_SCRIPT failed` or an `Uncaught` line |
| A check passes alone but fails in the suite | A previous run's localStorage leaked; the tools set `XDG_CONFIG_HOME` per run, so do the same |
| Unit test fails in only one zone | A date was built with UTC (`toISOString`, `Date.UTC`) or across a DST change; use local keys |
| A shot is missing from the screenshot folder | Its name ends in `-alarm.png`, which `shots.sh` deletes |
| `npm test` finds no tests on Node 22 | `node --test test/` needs `test/index.js` to require the test file |
| Two builds give different hashes | A file's time or order changed; keep `SOURCE_DATE_EPOCH`, the `touch` step and the sorted `zip -X -D` |
| A change in `styles.css` breaks a theme | Put new rules in `themes.css`, after the base, and use tokens |
